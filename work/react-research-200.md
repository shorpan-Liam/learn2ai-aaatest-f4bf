## 一、React 的定位与核心思想

【事实】React 是一个用于构建用户界面的 JavaScript 库，由 Meta（原 Facebook）于 2013 年开源；截至 2026 年 9 月 30 日，最新稳定版本为 React 19.3（2026 年 9 月 9 日发布）。它的核心思想可以概括为一句「界面是数据的函数」：给定同样的数据就渲染出同样的界面，数据变化后由 React 负责计算并只更新界面上真正变化的部分，开发者不必手动操作 DOM。

【事实】React 最鲜明的两个特征是**组件化**和**声明式 UI**。组件就是「返回界面标记的 JavaScript 函数」，函数名必须大写开头，这样才能和普通 HTML 标签区分开；声明式则意味着开发者描述「界面应该长什么样」，而不必用 `document.createElement` 一步步命令式地拼装页面。

【观点】我认为 React 最巧妙的地方，是把「界面现在是什么状态」和「界面该长什么样」拆成了两件事：只要数据是对的，界面就会是对的。我写代码时的关注点因此从「怎么改 DOM」转移到「数据现在是什么」，需要同时记住的东西变少了。

## 二、它解决的主要问题：与直接操作 DOM 相比

【事实】直接用原生 JavaScript 操作 DOM 时，页面数据和 DOM 之间没有同步机制，开发者必须自己记住「界面上现在有什么」并手动增删改节点。列表增删、条件显示、表单输入这类操作很容易漏改某一处，于是出现数据和界面不一致的问题。

【事实】React 用虚拟 DOM 加差异比较来处理这件事：数据变化后，React 重新计算出新的界面描述，和上一次的结果比较，只把真正变化的部分提交给浏览器；渲染列表时还可以用 `key` 标识每一项的身份，从而正确地复用或移动节点。

【观点】我的判断是，React 的优势其实不在「更快」——对交互简单的页面，直接操作 DOM 往往性能更好，代码也更少——而在于**可维护性**。它把「数据变了一致性由谁保证」这件容易出错的事交给了框架，让复杂交互的代码变得可预测。页面越复杂、共享状态越多，这份收益就越明显，也就越能覆盖学习它的成本。

## 三、当前生态与使用情况

【事实】React 只负责视图层这一件事，所以真实项目通常由多块拼成：构建工具用 Vite，路由用 React Router，元框架用 Next.js，状态管理用 Zustand 或 Redux，等等。官方文档显示，2025 年 2 月 14 日起官方已弃用 Create React App，并建议新项目改用框架或 Vite 这类构建工具——这与课程讲义推荐 Vite 是一致的。

【事实】我额外核对到几条讲义里尚未提到的新进展：一是 React Compiler v1.0 已于 2025 年 10 月 7 日发布稳定版，可以由编译器自动完成过去需要手动 `useMemo`、`useCallback` 才做的优化；二是 React 19.2（2025 年 10 月）带来了 `Activity`、`useEffectEvent` 等能力；三是 React 19.3（2026 年 9 月）把 `View Transitions`、`Fragment Refs` 转为稳定 API，并新增了 `browser()`；四是 React 项目已交由 Linux 基金会下的 React Foundation 托管（2026 年 2 月 24 日正式成立）。

【观点】从这些变化看，React 已进入「稳定演进、补齐使用体验」的阶段，而不是在频繁推翻自己的旧设计。对一个打算长期投入的前端方向来说，这反而是一个加分项。

## 四、我的一句话结论

【观点】**需要长期维护、交互状态复杂、多人协作的界面（后台管理系统、内容平台、跨端应用）适合用 React；只放少量静态内容、几乎没有交互的页面（企业官网、活动页、静态博客）就没必要用它，用原生 HTML/CSS/JavaScript 或静态生成工具就够了，引入 React 只会平白增加构建与维护的复杂度。**
